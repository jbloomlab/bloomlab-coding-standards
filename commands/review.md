---
description: Structural code review against lab standards (run before opening a PR)
argument-hint: "[branch | PR number | path]"
allowed-tools: Read, Grep, Glob, Write, Task, Agent, Bash(git diff:*), Bash(git log:*), Bash(git show:*), Bash(git status:*), Bash(git branch:*), Bash(git rev-parse:*), Bash(git rev-list:*), Bash(git remote:*), Bash(git submodule status:*), Bash(git -C bloomlab-code-standards fetch:*), Bash(gh pr view:*), Bash(ruff:*), Bash(black:*), Bash(snakefmt:*), Bash(snakemake:*)
---

Review the current changes against the lab coding standards in `bloomlab-code-standards/CLAUDE.md`. If an argument is given, review that instead (a branch, PR number, or path): $ARGUMENTS — ignore that placeholder if it is empty or arrives uninterpreted, which is what happens when this file is read directly rather than run as a slash command. Otherwise review the diff of the current branch against `main` (e.g. `git diff main...HEAD`), plus any uncommitted changes.

This is a **structural** review. You are checking whether the change keeps scientific decisions visible and the codebase reviewable — not whether the science is correct. Where the science is in question, your job is to surface it for a human, not to adjudicate it.

**Run the review in a fresh subagent.** Dispatch one general-purpose subagent and give it only the diff range to review, the path to `bloomlab-code-standards/CLAUDE.md`, and the checklist below. Do not pass it anything else from this session. If this session wrote the code under review, a same-session review is the author grading their own work, and it grades kindly. Write the review from what the subagent reports back.

**The review changes nothing.** Do not edit, fix, or reformat any file in the repository while producing it — fixing a finding mid-review invalidates the very diff the review describes. Fixes come after the review has been presented, and are followed by a fresh review. (Writing the review itself to `_review.md`, below, is the one file this command creates.)

Check, in order of importance:

1. **Input data records what happened.** Inputs may be tables, a directory per unit whose filenames are the schema, YAML, or sequences with a metadata sidecar — no shape is required, so do not flag one for not being a CSV; read "column" below as whatever the shape's equivalent is (a field, a key, a file in a unit's directory). For any file added or changed under `data/`: does a single column carry more than one job (an identity, a control kind, a replicate index, a note)? Does an identifier pack attributes into a name — a year, a passage, a subtype, a batch — rather than giving each its own column, so that it cannot be joined on or validated and changes whenever an attribute is corrected? Does a column use a sentinel value to mean "none" or "not applicable" instead of an explicit kind column with the inapplicable field left empty? Is a fact that was known at the bench being reconstructed downstream by a heuristic — a nearest match, a name prefix, a hardcoded list of positions — rather than recorded? **Apply the diagnostic: if code or configuration has to be told what a value in a data file means, the data file is wrong.** A config key that translates a value, or an exclusion list that exists because a value is mislabeled, is a finding: name the key and state what the data file should record instead. For *downloaded* data (a database pull, a file from another repository), does it record its source URL or query and its download date somewhere durable — a neighboring README, the directory name, or a tracked date file? Do not raise this for files the experimenters produced themselves, such as plate layouts or manifests; those have no external provenance. Conversely, do not flag a data file for recording a fact that happens to be derivable from another file — that is a different observation, not duplication — but do check that code carrying a derivable column as a cross-check asserts the two agree. Where the file is tabular, are missing values empty fields rather than a mixture of `NA`, `-`, `?`, and `999`, and is every meaning carried by content rather than by formatting, color, or position?

2. **Config/code separation.** Does the diff introduce or change any experimental parameter inside code — sample IDs, inclusion/exclusion lists, thresholds, cutoffs, reference or database versions, statistical method choices, hyperparameters, seeds, hardcoded paths? Each is a finding: quote the line and state which `config.yml` key it should become. Is any path absolute rather than relative to the repository root or to a root named in `config.yml`? (Only large raw sequencing files on the cluster are exempt, and only when named in `config.yml` or a manifest.) Is a required config key read with `.get(key, default)` rather than `config["key"]`, silently substituting a scientific parameter? Does the config enumerate something derivable from the data (sample or sera names, well lists)? Is the new configuration more elaborate than it needs to be — a key, a nesting level, or an option nothing requires? Does it copy-paste a block that a YAML anchor would state once (or that could be derived from the data instead of configured)? Judge repetition by severity: a set of per-experiment entries — one block per plate, run, or batch — that differ in a field or two is a **suggestion** at most, since each entry reads as a standalone record of one experiment; reserve **Must fix** for blocks identical in every field, a block repeated across unrelated sections, or enough entries that a reader cannot see which fields vary. Conversely, if code behavior changed in a scientifically meaningful way with no corresponding config diff, flag that.

3. **Directional integrity.** Does any code write into `data/` or `config.yml`? Does anything read from `results/` as if it were primary input to the same pipeline? Were files in `data/` modified in the diff without explanation in the commit message or PR description? (Auspice JSONs in `auspice/`, and a data file built by a documented hand-run script kept beside it, are the recognized exceptions.)

4. **Validation and failure behavior.** Do new inputs get validated at the boundary (required keys/columns, unique IDs, allowed values, files exist)? Do not ask for validation of the *scientific content* of an experimental parameter — that a set of primer indices is distinct, that a dilution series is right, that a date is correct. Those are bench facts confirmed by a human, and calling for code to check them is a finding you should not raise. Are identifiers read as strings (`dtype=str` when reading a table), so that sample `007` cannot silently become `7`? Any bare `except`, silent `errors="coerce"` + `dropna`, default fallbacks for scientific parameters, or other patterns that let bad input pass silently? Are error messages informative (file, column, offending values)? Where fail-fast is deliberately relaxed, is the default applied in one place and justified in a comment?

5. **Redundancy, modularity, and length.** Does the diff duplicate existing logic (copy-pasted blocks, near-identical scripts, re-implemented utility functions)? Point to the existing code it duplicates. Does it recompute or re-plot something an included lab pipeline already produces? Are new scripts small and single-purpose, or is the change appending unrelated logic to an existing script? Is the code longer than the problem requires — unused helper layers, configurability nobody asked for, defensive branches for cases that cannot arise? Be specific about what to cut. In a repository whose code other projects import — a lab package, or a pipeline submodule — does new or changed shared functionality come with a test? In an analysis project do not raise tests at all; they are not required there.

6. **Obsolete files.** Does the change leave anything stranded — a data file no config key or script reads, a script no rule runs, a rule no target needs, a config key nothing looks up, results superseded by what this change produces? Look beyond the diff for these where the change makes them obsolete. List each with its path and what used to use it, and suggest pruning; for anything in `data/`, raise it as a question rather than a fix, since it may be the only record of an experiment. Separately, does the diff commit scratch work — an exploratory script, an intermediate table, a note-to-self — that should have been `_`-prefixed and left untracked?

7. **Pipeline hygiene.** Are new analysis steps expressed as Snakemake rules with explicit `input`, `output`, `params`, and `log`, sourced from config and data? Does every new rule declare `log:`, and does a `script:` rule's script redirect stdout and stderr into it? Does anything reach a script other than through `input`, `params`, or `wildcards` — an implicit default, a global, a path the script reconstructs itself? Do Python steps use the `script:` directive rather than `shell:`? Is analysis logic sitting in a `.smk` file that belongs in a script? Do rules write only under `results/` (or `auspice/`)? Are environments pinned consistently with the rest of the project? Does a new or changed `environment.yml` list `conda-forge` before `bioconda` with `nodefaults` and no `defaults`, and — if it is the project's own environment rather than a lab pipeline's — include the tools the project's code is checked with (`ruff` and `black`, plus `snakemake` and `snakefmt` where there is a workflow)? Is `Snakefile` long enough (beyond a few hundred lines) that its rules should be split into `rules/*.smk`?

8. **Notebooks and non-pipeline analyses.** Is newly added analysis in a notebook where a script would be shorter and clearer? Does the pipeline depend on a notebook that is not run by a rule with explicit inputs and outputs? Does an addition to `non-pipeline_analyses/` re-implement something the pipeline already does, or commit bulk generated output?

9. **Results tracking.** Does the diff add large or binary regenerable output to git? Two things about reference `.gitignore` files, and only these two pipelines have one: `seqneut-pipeline/test_example/.gitignore` and `dms-vep-pipeline-3/test_example/.gitignore`. **Never flag a tracked path under `results/` that one of those files re-includes** — which of a pipeline's outputs are tracked is settled in the pipeline and is not a project-level finding. And **check coverage in the other direction on every review** where the project includes one of those submodules, whether or not `.gitignore` is in the diff: read the pipeline's `test_example/.gitignore` and the project's `.gitignore`, strip comments and blank lines from both, and compare the remaining patterns as sets. Any pattern in the reference and absent from the project's is a **Must fix** — list the missing patterns verbatim, since each is a pipeline output the project has silently stopped tracking. Comments, ordering, and the project's own additional patterns are all fine and are not findings. Where the project includes both pipelines it must cover the union; where it includes neither, this check does not apply and you report nothing about it. Beyond that, a deliberately tracked intermediate is the project's choice: note what it costs as the project grows if a change multiplies it, but do not raise the choice itself. Does the diff add a key scientific result that is *not* tracked and should be, so that someone can read the main results without running the pipeline? Does a new output CSV write floats at full precision rather than a sensible number of significant digits (5 by default, or a deliberately chosen alternative), or write a meaningless integer row index that should have been suppressed with `index=False`? Does a new Vega-Altair chart embed more data than it draws — columns it never encodes, rows it filters in the encoding rather than before construction, or per-entity metadata repeated on every row of a long table that a `.transform_lookup` would carry once? A chart file is as large as the dataframe handed to it, so this is a tracking question as much as a plotting one.

10. **Lab software.** Does the change work around a limitation in a lab-maintained package (`seqneut-pipeline`, `dms-vep-pipeline-3`, `neutcurve`, `polyclonal`, `nextstrain-prot-titers-tree`, and similar) — a wrapper that reshapes its output, a copied-and-edited function — rather than opening an issue upstream? Say which repository the issue belongs in. Does the change add project-specific rules or data to a shared submodule?

11. **Scope and clarity.** **Does this change do more than one conceptually distinct thing?** Unrelated fixes, renames, reformatting, or refactors bundled with the substantive change are a finding on their own: say which commits or pull requests the work should be split into. Would a scientist be able to see every scientific decision in this diff by reading only `config.yml`, the files in `data/`, and the rules?

12. **Documentation.** Does the diff restate configuration values, thresholds, counts, or file lists in Markdown instead of saying where they are configured? Does it document columns in prose that the file header, config comments, or validation messages already make clear? (Documenting columns is legitimate where the file is hand-authored or carries a convention a reader could not infer — judge whether this instance earns it, rather than flagging all column documentation.) Does `CLAUDE.md` gain project description, per-rule, or per-key documentation that belongs in `README.md` or `config.yml`? Does a change that adds, removes, or redirects an analysis or a result file leave `README.md` stale? Do any new comments or docs narrate the change rather than describe the result — text saying what something "now" does, what it used to do, or why the new approach replaced the old one? That belongs in the commit message, not the code.

13. **Tooling.** Confirm the changed code passes `ruff`, `black`, `snakefmt`, and `snakemake --lint`. Run them if they are available; if they cannot be run, say so rather than assuming they pass.

Before writing the review, check whether the standards submodule is up to date. This must never block or fail the review: run `git -C bloomlab-code-standards fetch --quiet origin`, then `git -C bloomlab-code-standards rev-list --count HEAD..origin/HEAD`, falling back to `origin/main` where `origin/HEAD` is not set (which is common in a submodule). If the fetch or comparison fails for any reason (offline, no remote, detached oddities), record `freshness not checked` in the stamp and move on. If the count is zero, record `up to date`; if greater than zero, record `behind origin by N commits` and add a one-line note at the end of the review reminding the author to update: `git submodule update --remote bloomlab-code-standards && git add bloomlab-code-standards && git commit -m "Update lab coding standards"`.

Then write the review with exactly these sections, beginning with a provenance stamp:

- **Provenance stamp** — a short fenced block at the very top, populated from actual git commands (never from memory):

  ```
  bloomlab-code-standards structural review
  repo:      <git remote get-url origin, or "no remote">
  branch:    <git rev-parse --abbrev-ref HEAD>
  reviewed:  <git rev-parse HEAD>  (HEAD at time of review)
  diff:      <base>...<head range actually reviewed, e.g. main...HEAD>
  tree:      clean | DIRTY (uncommitted changes were included in this review)
  standards: <short SHA of the bloomlab-code-standards submodule>  (up to date | behind origin by N commits | freshness not checked)
  date:      <UTC timestamp>
  ```

  If the working tree is dirty, say so in the stamp and warn at the end of the review that this review cannot be verified against any pushed commit until the changes are committed.

- **Summary** — 2–4 sentences: what the change does and whether it is structurally sound.
- **Scientific decisions in this diff** — every change to samples, parameters, methods, or data handling, stated plainly so a human reviewer can evaluate the science. If none, say "None."
- **Scope** — whether this is one conceptual change. If it is not, list the distinct changes bundled together and how to split them. If it is, say "Single change."
- **Must fix** — standards violations, each with file:line, the problem, and a concrete fix. If none, say "None."
- **Suggestions** — non-blocking improvements. Be brief; do not pad this section.
- **Questions for the author** — anything requiring human judgment about experimental design or data semantics. Ask; do not assume.

Be specific and terse. Do not praise. Do not restate the diff. Do not comment on formatting or naming taste unless it violates a written standard. If the change is clean, a short review is the correct review.

## Posting the review

**Never post without an explicit yes.** Always present the review first and ask before posting. (`gh pr comment` is deliberately left out of this command's `allowed-tools`, so posting raises a permission prompt as well.) Declining is a normal outcome — print the review and stop. Do not edit the review between presenting it and posting it, even if asked for wording changes: findings are discussed on the pull request, not removed before it sees them.

One invariant governs the rest: **the review attached to a pull request must describe that pull request's head commit.** The `reviewed:` SHA in the stamp is what lets a reader trust the review, and a review of some other commit is worse than no review at all. Note what this does *not* require — a review that reports findings is still worth posting. Fixing them first is a choice, not an obligation, and a posted review whose findings are then argued out on the pull request is a better record than a clean one.

Save the full review, stamp included, to `_review.md` at the repository root (the `_*` convention keeps it untracked; add `_*` to `.gitignore` if the project does not have it yet). Then check whether a pull request exists for what was reviewed — `gh pr view --json number,url`, or `gh pr view <number> --json number,url` if a number was given as the argument — and:

- **A pull request exists.** Ask whether to post the review to it. On confirmation, post it verbatim: `gh pr comment --body-file _review.md`. If more commits are pushed afterwards, that stamp goes stale; re-run the review and post again.
- **No pull request yet.** This is the normal case — reviewing before opening the pull request is the point of running this early. Present the review and say that once the branch is pushed and the pull request opened, running the review again will offer to post it. Do not try to preserve this review for posting later: re-running takes seconds, and only a fresh run is guaranteed to match the head commit.

Whoever runs the review posts it under their own GitHub account, and nothing here assumes that is the author. A review run by a co-author or by the PI satisfies the requirement exactly as well, provided its stamp matches the head commit.

If `gh` is unavailable or unauthenticated, do not treat this as an error and do not get stuck on it. Offer once to fix it (install `gh`, or walk through `gh auth login` interactively). If that is declined or fails for any reason, fall back immediately: the review is in `_review.md`, and pasting it into a pull request comment unmodified, stamp included, is always acceptable. Never let GitHub tooling block a review or a pull request.
